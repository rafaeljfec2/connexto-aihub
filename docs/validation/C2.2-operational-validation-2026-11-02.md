## 2. Runtime-state diagnosis

1. At startup, `ConfigModule` loads the persisted provider record and
   `Service.apply` retrieves its sealed credential, decrypts it with the
   provider-bound credential cipher, and applies settings to the adapter bound
   to that provider ID.
2. The provider Manager starts after configuration bootstrap. If
   `OpenRouterClient.Enabled()` is false because the credential is absent, the
   Manager records `disabled`. For an enabled adapter, it probes the model-list
   endpoint and records `healthy` or `unhealthy`.
3. An administrative PATCH persists the changes and reconfigures only the
   matching Registry adapter. Before this correction, that path did not notify
   the Manager, so its startup probe state stayed unchanged.
4. `/diagnostics/providers` serializes the Manager's statuses. `enabled` comes
   from the adapter's current `Enabled()` value, while `state` came from the
   Manager's stored probe result. This produced `enabled=true` with stale
   `state=disabled` after adding a credential.
5. Catalog synchronization consumes provider statuses to decide whether to
   run or skip a sync. It owns a separate catalog-sync state and does not update
   the provider Manager's runtime health state.

**Root cause:** runtime reconfiguration updated the adapter but left the
Manager's prior connectivity state in memory. Persisted configuration, adapter
availability, and Manager probe state could consequently disagree.

**Correction:** Registry reconfiguration now notifies the provider Manager
after a successful adapter update. The Manager invalidates that provider's
prior probe result to `unknown`. The current Manager only probes during process
startup, so this state remains `unknown` until a future startup probe. This
avoids claiming health without a check. Name-only updates do not reconfigure the
adapter or discard a valid probe result.

The new regression test covers missing credential → disabled → credential
update → enabled/unknown → successful local probe → healthy → credential
rotation → enabled/unknown. It also verifies that a name-only update preserves
the healthy state. Its fake upstream is an in-process `httptest` server.

## 3. HTTP 429 diagnosis

The C2.1 report records two upstream HTTP 429 responses:

- `google/gemma-4-26b-a4b-it:free`
- `liquid/lfm-2.5-2.6b:free`

The prior authenticated model listing returned HTTP 200 with 415 entries, 17
showing zero prompt and completion prices. This proves the key was accepted by
the model-list route at that time; it does not prove generation availability
for a particular model.

The adapter preserves an upstream error status and replaces an upstream error
body with a generic error to prevent credential disclosure. The execution
lifecycle commits the received status to the gateway response and records the
upstream status with provider/model metadata. The captured C2.1 report contains
the 429 status but no upstream response body or rate-limit/retry headers, so
the exact provider error cannot be recovered from the available evidence.
Retry-related upstream headers are not copied to the gateway response.

OpenRouter's current limits documentation identifies two sources for HTTP
429: platform limits (free-model per-minute/daily quotas or abuse protection)
and upstream provider rate limiting or capacity. Platform-limit responses may
carry `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset`; an
upstream provider error may include `error.metadata.provider_code`, and a
provider retry hint may result in `Retry-After`. `GET /api/v1/key` reports
account-specific `free_model_daily_requests` counters. OpenRouter also states
that failed free-model attempts count toward the daily cap.

The captured evidence cannot distinguish these cases. The latest HTTP 429
confirms a rate-limit rejection on the OpenRouter request path: the adapter
returns the upstream status unchanged. However, `sanitizeOpenRouterErrorResponse`
replaces the upstream body with `OpenRouter request failed`, and the gateway
response sink forwards only status, content type, and body. Execution logs
retain provider/model IDs, status, cause, and duration, but not the upstream
error metadata or rate-limit headers. The C2.1 captures contain no original
body or headers; the C2.2 response was likewise recorded only as the generic
sanitized error. This information cannot be recovered from the saved evidence.

The prior HTTP 200 model listing proves the key was accepted for catalog
access, not that the account had generation quota. A later read-only
`GET /api/v1/key` using the current literal key assignment in `.bashrc` returned
HTTP 200 with `free_model_daily_requests` at 131 used, 1,000 limit, and 869
remaining (`is_free_tier=false`). The C2.1 record says this assignment was used
to configure OpenRouter, but the current `.bashrc` key was not compared with
the sealed database credential. Therefore, the daily cap was not exhausted
for the queried key at check time; the result applies to the AI Hub credential
only if it is still the same key. The API does not report the per-minute limit.

The three `:free` 429 attempts remain consistent with an account/platform
per-minute limit or abuse protection, or with provider-side rate limiting or
capacity. The evidence does not identify which one occurred. No adapter defect
is established.

Code inspection confirms the observability gap: `internal/providers/openrouter.go`
preserves the upstream status but replaces every non-2xx body with a generic
error; `internal/gateway/responses_handler.go` commits only status and content
type before forwarding the sanitized body. It does not forward upstream rate
limit headers. `internal/execution/manager.go` logs provider/model IDs, outcome,
cause, upstream status, and duration, but not upstream error metadata or
headers. The current shell had no `OPENROUTER_API_KEY` environment variable;
the literal assignment in `.bashrc` was read in process memory only for the
read-only quota query. Its value was not printed or written anywhere, and it
was not compared with the protected database credential. No additional
generation request was made for this diagnosis.

Sources: [OpenRouter API limits](https://openrouter.ai/docs/api_reference/limits),
[OpenRouter free models](https://openrouter.ai/collections/free-models), and
[OpenRouter models API](https://openrouter.ai/docs/api/api-reference/models/get-models).

At the time of the initial C2.2 diagnosis, no additional provider call had been

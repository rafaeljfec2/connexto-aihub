## 2. Diagnosis and technical decisions

Before C2.4, `providers.Manager.Start` called each enabled adapter's model-list
endpoint and initialized the Manager as `healthy` or `unhealthy`. Separately,
`catalog.Manager.Start` launched a startup sync only when the provider state was
already `healthy`; an `unknown` state is persisted as a skipped sync.

C2.4 changes the lifecycle as follows:

1. The existing provider configuration module still loads persisted records,
   decrypts credentials and applies each configuration to its provider-ID-bound
   runtime before the Manager starts.
2. `Manager.Start` makes no network request. Enabled providers begin as
   `unknown`; disabled or credentialless providers remain `disabled`.
3. The existing `POST /api/providers/{id}/validate` route remains the explicit
   check. It probes only the requested persisted provider configuration, with
   a ten-second deadline and request cancellation, using the provider's model
   listing endpoint. It does not submit Responses or generate content.
4. Registry health notifications update only the Manager's runtime status.
   Caller cancellation leaves the status `unknown`; a timeout or other probe
   failure marks it `unhealthy`; success marks it `healthy`.
5. A per-provider runtime version discards results from a check that finishes
   after that provider is reconfigured. Endpoint or credential changes still
   invalidate health; name-only changes preserve it.
6. The validation handler returns generic errors and no longer logs raw probe
   errors, so secret-shaped upstream errors cannot reach HTTP responses or logs.

No catalog implementation change was needed: its existing startup behavior
skips `unknown` providers. Provider selection, OpenCode Go default behavior,
execution admission for disabled providers and the absence of automatic
fallback remain unchanged.

## 3. Automated evidence

Regression coverage added or updated:

- Manager startup tests assert zero model-list requests and initial `unknown`
  state for enabled providers.
- Multi-provider configuration recovery tests reconstruct runtimes from
  persisted fake-repository credentials and assert that Manager startup leaves
  both providers `unknown` without probing.
- Service and gateway tests verify that an explicit validation updates only
  the requested provider, including success and failure paths.
- Deadline and cancellation tests verify context propagation and the resulting
  health state.
- A concurrent credential-rotation test proves that a stale in-flight result
  cannot overwrite the new `unknown` state.
- The admin route test injects a secret-shaped probe error and verifies that it
  appears neither in the response nor in logs.
- E07's local hub fixture now expects `unknown` at startup and zero fake
  provider calls; its unauthenticated-request budget assertion remains intact.
- Existing provider-selection and no-fallback regressions remain covered by the
  full suite.

subtests, and 0 failing test events across 22 packages with tests**. Two
additional packages reported no test files.

## 5. Operational validation and limits

The local E07 hub fixture started with a static fake transport. Its tests
passed with zero startup transport calls and `unknown` provider state. The
persisted-credential restart regression uses a fake repository and verifies
that both stored credentials are applied independently before health state is
initialized.

A live restart against the existing PostgreSQL-backed Hub was **not
performed**. An `ai-hub` process was already present and port 8080 was active;
it was left undisturbed. Consequently, real PostgreSQL credential recovery
after restart remains **not operationally verified** in this increment. No
OpenRouter health check, model listing, Responses request or inference call was
made.

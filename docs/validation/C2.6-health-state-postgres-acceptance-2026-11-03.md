## 2. Health-state diagnosis and semantics

The current code path is provider-specific and synchronous:

1. `Service.Validate` reads the persisted endpoint and decrypts the stored
   credential, then invokes the probe registered for that provider type.
2. The probe result is reported to the Registry health observer unless that
   provider was reconfigured while the probe was in flight.
3. The Manager maps a successful current probe to `healthy`, a failed or timed
   out probe to `unhealthy`, caller cancellation to `unknown`, and a disabled or
   credentialless runtime to `disabled`.
4. OpenRouter's probe uses the configured authenticated model-list endpoint and
   accepts HTTP 200. It does not submit Responses or perform inference.

The validation route's `reachable` response label and the diagnostics health
state are separate fields with separate meanings. `reachable` means the
configured probe succeeded. The diagnostic `state` records the latest health
evidence. For OpenRouter, HTTP 200 from its authenticated model-list operation
is the adapter's defined functional health signal; it does not establish that a
particular model or feature can generate a response. Diagnostic `enabled`
represents runtime availability: the bound adapter is enabled and has its
credential. Availability gates execution independently from health.

The service/admin regression test uses the real `ProbeOpenRouterEndpoint`
against a controlled local HTTP server. It verifies `unknown` before
validation, the authenticated `GET /api/v1/models` request, `reachable` in the
validation response, and `healthy` through the HTTP diagnostics route
afterward.

The discrepancy was also reproduced in the existing Hub process. A single
explicit OpenRouter validation there returned HTTP 200 `reachable`; the first
diagnostics request used the administrative key and returned 401, then a GET
with the gateway key returned HTTP 200 with state `unknown`. After restarting
only the Hub, a single explicit validation returned HTTP 200 `reachable` and
the subsequent authenticated diagnostics GET returned HTTP 200 with
`enabled=true`, `state=healthy`. The restart therefore cleared the observed
stuck state in the prior process. Its exact in-process cause was not isolated;
no source-level runtime fix is claimed. No inference was performed.

# E08.5 — Routing observability and end-to-end acceptance

**Status:** accepted (local) — see `docs/decisions/e08.5-formal-acceptance-2026-11-03.md`

## Scope

Content-free structured logs for intelligent routing decisions on the Responses gateway path, plus automated acceptance tests. No E06 schema changes, no new durable query API, no LLM classifier.

## Log event

Message: `routing decision` (slog, same logger as execution lifecycle).

Emitted when `ResponsesRouting` is configured. Rejections log immediately; successful selections log once after `Execute` returns so `reached_execution` matches admission. Log order on the success path is therefore `execution started` → `execution finished` → `routing decision` for synchronous responses; correlate events by `request_id` (production: `server.withCorrelationID`).

### Fields (bounded, content-free)

| Field | Meaning |
| --- | --- |
| `intelligent_routing` | Always `true` when this event is emitted |
| `request_id` | Correlation ID from request context |
| `explicit_provider` | Normalized provider selector header value (may be empty) |
| `reached_execution` | `true` only when `execution.Manager.Execute` admits the command (`err == nil`); `false` on routing/provider gate failures or admission errors |
| `rejection` | Stable routing rejection code when selection failed |
| `structural_rejection` | `invalid_request` when structure validation failed before eligibility |
| `selection_origin` | Contract origin when selected |
| `provider_id`, `model_id` | Selected target when applicable |
| `criteria` | Rule identifiers influencing the decision |
| `eligible_count`, `evaluated_count` | Eligibility summary |
| `coverage_complete_fresh` | Coverage flag from eligibility |
| `requirement_unmapped` | Structural capability projection flag |
| `required_capabilities` | Normalized capability requirements (when present) |
| `excluded_reason_codes` | Deduped eligibility reason codes for ineligible candidates (capped) |

Terminal execution outcome remains on existing `execution finished` logs and E06 records (successful executions only). Correlate by `request_id`.

## Implementation

- `internal/routing/observability.go` — `LogDecision`, `DecisionLogInput`
- `internal/routing/selector.go` — default `Criteria` on rejections (`rejection:<code>`)
- `internal/gateway/responses_handler.go` — log after routing / provider gate
- `internal/gateway/responses_routing.go` — returns `RoutingDecision` alongside route result

## Tests

| File | Proves |
| --- | --- |
| `internal/routing/observability_test.go` | Log shape, reason codes, default criteria, no payload leakage |
| `internal/routing/selector_regression_test.go` | Stale catalog + explicit provider + multiple eligible → `routing_unavailable` |
| `internal/gateway/responses_routing_observability_test.go` | HTTP E2E: success, ambiguity rejection, structural rejection, `request_id` correlation |

## E08.3 follow-ups addressed

| Topic | Action |
| --- | --- |
| Empty `Criteria` on rejections | Default `rejection:<code>` criteria |
| Explicit provider + stale catalog + multiple eligible | Regression test + existing selector behavior (`routing_unavailable` when stale catalog yields zero eligible; ambiguity requires fresh coverage) |
| `ExplicitModel` / model `TrimSpace` | Gateway uses structural validation (empty whitespace model → `invalid_request`); selector trims explicit provider and `ExplicitModel` field |

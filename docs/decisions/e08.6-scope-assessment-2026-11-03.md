# E08.6 scope assessment — Task classification (planning)

**Date:** 2026-11-03

**Status:** recommendation — **do not authorize E08.6 for MVP**

## Question

Does E08.6 (bounded structural task classification / Request Understanding) add **real value** to the Connexto AI Hub MVP now that E08.1–E08.5 are complete?

## SPEC intent (E08.6)

From `docs/specs/E08-intelligent-routing.md`:

- **Request Understanding** may derive task metadata from **bounded structural fields** and explicit preferences — not message text without separate approval.
- E08.6 is labeled **future vision — not authorized** by the current SPEC.
- E08.3 deterministic selector remains the **baseline** when no classifier runs.
- Multiple eligible candidates still produce **`routing_ambiguous`** in MVP; there is **no ranking metric** in the catalog.

## What E08.6 would need to change behavior

Classification only matters if selection rules **consume** new metadata. Today:

1. **Eligibility** (E08.2) already projects capabilities from structural request features.
2. **Selection** (E08.3) picks at most one unambiguous eligible target or rejects.
3. **Ambiguity** is intentional when more than one eligible model remains — not an accident to “fix” with hidden tie-breaks.

Therefore E08.6 metadata alone (task type, complexity, modality hints) **does not resolve** the dominant MVP outcomes:

- `routing_ambiguous` — needs an **approved ranking or preference contract** (E08.7+), not labels alone.
- `routing_unavailable` / catalog stale — needs catalog/ops evidence, not classification.
- Explicit user provider/model — classifier must not override (ADR-022).

## Value analysis for MVP

| Potential benefit | MVP relevance | Assessment |
| --- | --- | --- |
| Reduce ambiguous rejections | High pain if users hit 409 often | **Low without E08.7 ranking**; classifier cannot pick among equals under current rules |
| Better default model when one eligible | Already covered by E08.3 compatibility / unique candidate rules | **Marginal** |
| Richer observability | Partially addressed by E08.5 reason codes and criteria | **Low incremental** |
| Product parity with Copilot/Cursor “Auto” | Evolutionary vision in SPEC §10 | **Out of MVP scope** by explicit decision |
| Input to future optimization profiles | Prerequisite for E08.7 | **Premature** until profiles are authorized |

## Risks if E08.6 is started early

- Scope creep into LLM-based classification despite ADR rejection for MVP.
- Pressure to break ambiguity rules with implicit ranking.
- New surface area before E08 local work is **published** and C2 debt is understood.
- Duplication with capability projection already in E08.2.

## Recommendation

| Decision | Rationale |
| --- | --- |
| **Do not start E08.6** as the next increment | MVP routing loop is complete; E08.6 does not unlock a committed product requirement without E08.7+ |
| **Next priorities (suggested)** | (1) Publish E08 local changes when approved; (2) C2 PostgreSQL validation; (3) SPEC table reconciliation; (4) Revisit E08.6 only after explicit product ask for “auto routing” with approved ranking/preferences |
| **If E08.6 is requested later** | Require a **new mini-SPEC**: bounded structural features only, no LLM by default, explicit mapping from metadata → eligibility or selection deltas, acceptance tests proving no regression to E08.3 determinism |

## Authorization boundary

E08.6, E08.7, and E08.8 remain **unauthorized** until project lead approves a separate specification. This assessment does not approve implementation.
